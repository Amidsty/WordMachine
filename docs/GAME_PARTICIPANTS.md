# 参赛关系与显式旧 JSON 转换

此前完成新对局的参赛关系存储、混合新旧来源的大厅查询，以及默认只读的单局转换工具。新局已接入 [答题关系表](GAME_ANSWERS.md)；新结算已写入 [评分流水](GAME_SETTLEMENTS.md)，已有快照及完整字段的旧答案可经 [独立受限工具](ANSWER_CONVERSION.md) 显式转换；不满足前提的记录需另审查，历史评分及其余 JSON 转换仍待完成，评分公式不变。仅在隔离 MySQL 合成数据上验证，未修改业务库或转换真实旧数据。

## 唯一数据来源

`0005_game_participants` 增加：

- `game.participant_mode`：0 为旧 `game.users` JSON；1 为关系表。迁移默认 0，新创建显式写入 1。
- `game.participant_count`：模式 0 必须为 NULL；模式 1 必须为正整数，用于检查关系行是否完整。CHECK 不允许 NULL 绕过模式 1 的数量要求。
- `game_participant`：`(game_id, user_id)` 主键防重复参赛；`(game_id, position)` 唯一，出场顺序从 0 开始；顺序非负、用户 ID 为正的 CHECK；到对局、用户的 RESTRICT 外键。
- `joined_at`、`recorded_at`：UTC 微秒时间。新加入者记录写入时点；旧数据转换不猜测加入时间，`joined_at=NULL`，`recorded_at` 记录转换写入时点，均不是提交时间保证。
- `(user_id, game_id)` 索引用于查找用户所参加的对局；对局的 `(participant_mode, status, id)` 索引用于分离存储来源和状态查询。

新创建的 `game.users=NULL`，不维护第二份成员 JSON。已显式转换的旧对局保留原 `game.users` 字节内容作存档，之后不再更新或用于成员判断。数量是完整性检查值，不是成员身份来源。

`game_participants.py` 适配两种存储，返回同一种有序用户 ID 列表。HTTP/Socket、轮次校验、房主权限、随机出场顺序和评分仍只在原共享服务实现一次。`question_mode` 与 `participant_mode` 独立：转换参赛关系不会恢复原题，也不会把 `legacy_live` 改成快照。

## 写入、锁与失败处理

1. 先预留请求 ID，再锁对局并检查版本，沿用原命令事务。
2. 更新参赛关系前，按**用户 ID 升序**取得所有相关用户的共享锁，再更新关系行。评分和管理员操作也按 ID 升序取得用户排他锁。
3. 不能直接按随机出场顺序触发用户 FK 检查，否则共享用户锁可能与另一局的评分锁倒置。新代码没有“先共享、再升级排他”的评分路径。
4. MySQL 唯一约束即时生效。重排先把现有位置移到不重叠的正数区间，再删除退出者、插入新成员并赋最终位置；不会为了重排删除再插入所有成员，现存行的时间不变。
5. 关系、人数、版本和请求回执同事务提交；任何异常整批回滚。开始后不再改变成员或顺序；未答题用户不因本次存储改造而被计分。

退出会删除该用户当前的参赛行，重新加入产生新时间；这张表不是完整的报名/退出事件日志。常规重排只发生在等待状态；显式转换只复制原顺序，不重排。

关系模式下，缺行、数量不符、重复/断裂顺序、房主缺失或异常元数据返回 `invalid_game_participants / 409`，不会回退到旧 JSON 或自动修复。FK 拒绝缺失用户/对局引用；只读审计还检查异常引用和旧模式下意外出现的关系行。与题目快照一样，不能据此宣称能识别所有合法形状的特权 SQL 篡改。

## 大厅与协议

- 对外返回的 `users/owner/is_joined/actions` 结构不变，不暴露存储标记或加入时间；当前页的关系行批量读取，再批量查询用户名，不为每个对局单独查成员。
- `active_game_id` 分别查询关系模式及旧 JSON 模式，再选最大 ID，仍独立于分页/过滤。旧 JSON 查询严格限定模式 0，模式 1 的存档不能把已退出者重新判为参赛者。
- 未转换的旧对局继续使用原 JSON 路径；无法解析的引用不悄悄修复。
- 索引和查询语义已验证，不等于生产规模性能验收。剩余旧 JSON 扫描、大 OFFSET、包含搜索和精确计数成本仍需实测。

## 默认只读的单局转换

**先按 [迁移指南](AUTH_MIGRATION.md) 确认目标库、停止旧写入、备份并在授权副本演练。** 先升级到 `0005_game_participants`，再使用工具。应用启动、HTTP/Socket 读写都不会自动转换旧对局。

```bash
# 默认只读事务：只审查某局参赛数据，输出 JSON 报告。
.venv/bin/python -m flask --app app convert-game-participants --game-id 123
# 例：{"game_id":123,"status":"ready","participants":2,"version":7}
```

工具检查有序成员 ID 唯一且为正、房主在成员中、用户引用存在、模式/数量元数据有效，以及没有意外的部分关系副本。保留已有软删除用户引用，不改变历史成员。**`ready` 只表示参赛数据可转换，不表示题目、答案、Perf、Rating 或整局已通过审计；仍须审查 `audit-legacy` 报告。** 不自动修复异常，失败报告仅含对局 ID、错误码和通用说明，不输出用户名或答案。

只有完成授权审查后，才手动执行：

```bash
# 7 必须替换为已审查报告中的版本；此命令会写入目标库。
.venv/bin/python -m flask --app app convert-game-participants \
  --game-id 123 --apply --expected-version 7
```

- `--apply` 缺少预期版本即拒绝。工具锁对局后重新检查，版本变化返回 `stale_game_version`；不依赖之前那次只读结果直接写入。
- 成员顺序逐项复制，新增关系行、切换模式/人数与版本加一同事务提交。不改原 JSON、题目来源、答案、评分、用户历史或已有请求回执。
- 版本增加使此前的新写命令明确冲突；既有成功请求仍重放原回执，不重复执行。转换不发送实时广播，页面通过现有读取/轮询恢复，建议维护窗口执行。
- 已是关系模式时只校验并返回 `already_normalized`，不重写时间或再加版本；指定的预期版本仍要匹配。提交结果不明时先重新只读核对，不自动重放写入。
- 拒绝覆盖部分关系行、推测缺失用户、合并重复成员或在版本耗尽时部分写入。每次只处理一局，没有隐含全库批量转换。

## 发布与回滚

本文对应 `0005_game_participants`；当前 head/readiness 以 [迁移指南](AUTH_MIGRATION.md) 为准。参赛迁移在 DDL 前检查同名部分结构、索引/约束冲突、signed INT 主键、可空旧 `users` 列和 InnoDB 引擎。结构迁移不解析或转换旧成员 JSON；已有旧值、版本、快照、回执均保留。

旧应用不认识关系模式，不能混合写入；已转换的存档 JSON 可能不再代表当前成员。禁止仅回退应用、清空关系表或把模式改回 0。MySQL DDL 可能部分提交，需匹配的已验证备份及开放写入后的数据保留方案；结构迁移拒绝破坏性 downgrade。

真实 MySQL 测试覆盖 HTTP/Socket 报名退出与完整评分、重排唯一约束、时间保留、重复回执、并发报名/开始/退出、跨局 FK/评分锁顺序、关系损坏、混合大厅查询、显式转换只读/回滚/版本竞争、约束和迁移保留数据。它们不能代替授权旧库副本、恢复演练或双用户浏览器验收。
