# Rating 第二批：统一流水基础与比赛结算接入（2A）

本文记录 **2A 交付时** 的比赛事件链边界，当时没有人工调分接口，0010 的约束只接受比赛事件。后续 [2B 人工调分](MANUAL_RATING.md) 已在本地源码实现，新增 `0012_manual_rating` 和独立审查/写入接口，不改写 0010；资料接口仍不能直接改余额。

## 已接入的记账路径

新迁移 `0010_rating_events`（接在 0009 后）新增 `rating_event` 与可空的 `user.rating_event_id`。每个用户的事件有独立 sequence、前驱、来源比赛流水、实际 before/delta/after、规则版本和记录时间。sequence 仅用于账户内次序；全局自增 ID 和时间均不是提交时钟。

- 升级时不生成任何事件，不修改旧 `game_rating`、`ratinghistory`、原余额或原比赛记录，不猜旧时间。
- 用户升级后的首次实际结算建立第一个事件，并用 `legacy_rating_id` 链接当时已有比赛流水前缀末行（可以为 NULL）。不把旧流水重新记一遍。
- 后续比赛先校验事件头、余额、来源及直接前驱/旧前缀锚点，再追加下一事件。旧 `rating_ledger_id` 保留为“最近比赛来源”的兼容投影；有事件头后，不能只凭该旧指针接受余额。
- 比赛结果头、`game_rating` 来源事实、`rating_event`、用户余额/两个指针及命令回执在同一事务提交。零增量仍有事件；零答题只有结算头，没有用户事件。
- 保持既有锁序：请求预留 → 当前对局 → 升序用户排他锁 → 已存在主键的当前共享读。不会为查头锁住另一场比赛，不对空流水范围加锁。
- 成功回执重放不追加事件。事件写入或后续步骤失败，答案、余额、所有流水及回执一起回滚。
- 历史读取/只读审计校验完整事件后缀覆盖、账户归属、序号/前驱连续、来源与余额一致，以及原比赛流水前缀。不会删除坏行、修复指针或回退掩盖坏数据。

写路径检查当前头及直接关联，不在每次结算扫描整段历史；完整链检查在历史读取和审计中进行。此处没有宣称能抵御拥有数据库写权限者同时伪造全部历史。异常数据须停写审查，不能手工修改余额后期待应用自愈。

源事实与事件包含相同余额字段，是有来源引用与一致性检查的记账投影，不是两套评分公式。评分仍只由原 `legacy-v1` 公式计算一次；历史读取不重新评分。INT 余额范围共用同一常量。

## 升级与部署

仅对已授权、停掉所有旧写入者、完成备份恢复及副本演练的库显式升级。0009 的旧 root 映射要求仍适用；先完成 [管理员等级迁移](ADMIN_LEVELS.md)，再：

```bash
python -m alembic upgrade 0010_rating_events
```

也可在已审查的完整升级窗口带 0009 的精确映射升级至 head。上述只是操作说明，不是本次已执行在用户库的操作。2A 当时的 readiness 要求为 `0010_rating_events`；后续词典倍率批次曾要求 `0011_dictionary_multipliers`，当前人工调分批次要求 `0012_manual_rating`。旧版本不能作为当前应用的就绪版本。旧应用不能与新应用混写。

迁移预先检查部分/自定义事件结构、依赖表引擎/主键类型；不自动接管已有同名表或列。MySQL DDL 隐式提交，失败可能留下部分结构，版本号不代表自动恢复。禁止 `stamp head`、盲目重试与自动 downgrade；使用经过验证的备份和匹配应用恢复。不承诺在线零阻塞 DDL。

新表和 FK 增加写入/锁及存储成本；历史读取多一次按参与用户批量加载事件的查询。未测生产容量、并发吞吐或 p95/p99，不能用原列表性能报告证明这次记账改造的性能。旧 schema 基准需配套旧运行代码，不能把当前服务跑在 0007/0008 上声称兼容。

## 2B 后续工作（现已在本地实现）

以下原定要求已落实到 [0012 人工调分](MANUAL_RATING.md)，不代表现有实例已迁移或功能已推送。

1. 以新修订扩展人工调整事件/不可重复请求记录；不能改写已经交付的 0010。
2. 4/5 级可自调或调严格下级，数据库锁内复核等级/状态；不比较双方 Rating 高低。审查余额版本、原因、密码再确认与审计同事务。
3. UUID 固定原意图、载荷指纹、唯一请求记录、原回执人工重试，失败不伪造成功。提交确认丢失不等于回滚。
4. 完整链检查、NULL/坏链拒绝，服务端计算设置目标余额的实际 delta，保留旧 JSON、Perf 与比赛次数。
5. 正在进行对局的用户拒绝调分；必须与开局/结束/结算共享用户锁协议，并用真实并发测试证明，不能只是先查一遍或隐藏按钮。
6. 比赛历史仍按比赛来源定位；人工事件不伪造 game_id。提供区分类型的流水展示、调分表单、审查/超时提示与能力返回，然后才开放入口。

## 2A 当时的定向验证（历史记录）

新增事件验证单元测试，以及真实 MySQL 的新事件/旧前缀衔接、同 UUID 不重记、跨局并发同账户串链、坏指针/来源/序号拒绝、SQL CHECK/FK/唯一约束、迁移不改旧行和部分结构拒绝测试。扩展原结算故障注入到事件 INSERT；保留同账户等待锁后当前读、不相交账户首次结算、HTTP/Socket 回执重启等原结算回归。

最终定向结果：**158 项相关单元测试、42 项真实 MySQL 用例通过**，114 个 Python 文件通过只读 Ruff lint/格式检查；`alembic heads` 为单一 `0010_rating_events`。日志：`/tmp/wm-rating-events-unit-final.log`、`/tmp/wm-rating-events-mysql-final.log`。

初轮保留失败记录：一个单元游标队列未包含新增事件查询；MySQL 用例中一个断言误把 CHECK 的 3819 异常当作 IntegrityError，另三个使用的测试历史读取助手未选新事件头。已修正测试读取/异常断言后复跑上述定向范围，未放宽服务端链校验。初轮日志是 `/tmp/wm-rating-events-unit.log`、`/tmp/wm-rating-events-mysql.log`，不是最终成功证据。

测试全部使用独立合成库，不是用户现有库；没有执行业务迁移，也没有将新增代码上传或部署。没有重跑全套 Python/浏览器矩阵，也未完成生产性能或现有库升级验收。
