# 用户、词典与对局迁移指南

## 状态与安全边界

已提供八版迁移及显式成员/受限答案转换工具，**未对现有业务数据库执行迁移、转换、修复或评分重算**。最新迁移仍为 `0008_list_indexes`，也是当前 head/readiness；后续 N1 仅改读取 SQL，没有新增迁移，详见 [索引迁移及代价](LIST_INDEXES.md)。已补齐隔离 MySQL 8.0 环境，252 项数据库集成用例（含合成旧数据迁移及本轮自然到期/限流恢复）通过，复现方式见 [测试环境指南](TEST_ENVIRONMENT.md)。另有真实 Chromium 用户/管理员/词典核心流程及维护权限矩阵通过，见 [管理浏览器验收](MANAGEMENT_BROWSER_TESTS.md)。本轮仅新增 [认证故障验证](AUTH_FAILURE_TESTS.md) 与 [N1 后续测量](LIST_FOLLOWUP.md)，运行源码、八版迁移和依赖未变。这些合成测试不等于真实旧数据副本迁移和备份恢复演练；后两者尚未运行，不能直接上线。

要求 MySQL 8.0.16+ / InnoDB，以执行 CHECK 和 `FOR SHARE`；迁移入口拒绝旧版本、MariaDB 和 SQLite。应用启动不迁移、不 `create_all`。`WM_DB_*` 决定显式迁移的目标库；数据库必须预先创建，迁移账号需要 DDL 权限。运行账号应仅授予所需的查询和数据读写权限；题目快照表只需 SELECT/INSERT，不应授予运行账号修改/删除快照的权限。参赛表不同，等待局报名/退出/重排需要 SELECT/INSERT/UPDATE/DELETE。答题表、结算头和评分流水只追加，运行账号仅需 SELECT/INSERT；用户余额和最新流水引用仍需 UPDATE。

## 版本内容

- `0001_legacy`：识别并接管完整的四张 InnoDB 旧表，或在空库创建它们。不复制、不重写已有业务记录；不完整结构、非 InnoDB 表或不相关的非空库会被拒绝。
- `0002_sessions_dict`：用户名非空及唯一索引、词典 `ownerid` 与外键、`auth_session`、`auth_rate_limit`。旧词典的 `ownerid` 保持 NULL，视为管理员维护的系统词典，不猜测归属。
- 用户名冲突按**数据库现有排序规则**检查，包含软删除用户；空用户名、重复用户名、不支持的列结构或部分迁移状态会停止升级，需人工审查。不会自动合并账户、删除记录或重算历史数据。
- 内部密码列仍叫 `user.pwhash`，只作存储字段。迁移不会修改密码；旧 SHA-256 仅在明文密码成功验证后升级成 scrypt。
- `0003_game_requests`：增加 `game.version`（非空、非负，旧行从版本基线 0 开始）和联合主键 `(actor_id, request_id)` 的请求记录表；预检同名部分结构、对局主键类型和引擎。旧 JSON、用户评分和评分历史不改写；不预生成历史请求记录。
- `0004_game_questions`：增加 `question_mode`、`dictname_snapshot` 和 `game_question`（题序主键、来源 ID 唯一、CHECK 与对局外键）。旧行标记为 0/NULL，不捕获今天的词典伪造历史题目；既有版本和请求回执也原样保留。新创建显式使用快照模式 1，详见 [题目快照指南](GAME_QUESTIONS.md)。
- `0005_game_participants`：增加 `participant_mode/count`、参赛表及唯一约束、外键、时间、索引；升级前对局统一保留模式 0/NULL，不自动解析/转换 JSON。新创建使用关系模式 1；单局显式转换工具默认只读，详见 [参赛关系指南](GAME_PARTICIPANTS.md)。
- `0006_game_answers`：增加 `answer_mode/count`、答题表的题序主键、快照/参赛者复合外键、索引、实际评分值与时间。升级前对局统一为 0/NULL，不自动转换旧答案；新局关系模式且 `result=NULL`，详见 [答题记录指南](GAME_ANSWERS.md)。预检部分/同名结构、父表 signed INT 主键、引擎及模式/结果列；不重写旧数据、已有快照、参赛行或回执。
- `0007_game_settlements`：增加结算模式、结算头和每局每人唯一的评分流水，保存结算前后 Rating、增量、Perf、规则版本与时间；增加用户最新流水引用及外键/索引。旧局模式为 0、用户引用为 NULL，不生成历史结算或改写 JSON；今后的实际结算统一写关系表，包括未结束旧局，详见 [结算流水指南](GAME_SETTLEMENTS.md)。
- `0008_list_indexes`：只增加 word `(dictid,deleted,id)`、user `(deleted,rating DESC,id)` 两个非唯一索引，不改业务行/JSON/会话/评分/回执。先预检两表，使用 INPLACE/LOCK=NONE，不回退 COPY；连接内每次元数据锁等待至多 30 秒（不放宽原更短限制），结束后恢复原值。它不是构建总时长上限，也不承诺无阻塞。读写/空间取舍和完整预检/降级边界见 [索引指南](LIST_INDEXES.md)。
- 新命令的业务写入、题目快照、参赛关系、答案、评分/余额/最新指针、版本及请求回执在同一事务中提交；锁顺序、请求表无用户外键的原因、兼容调用与回执保留边界见 [对局命令协议](GAME_COMMANDS.md)。现提供 [受限旧答案转换](ANSWER_CONVERSION.md)，仅接受既有快照/参赛关系及完整答题字段；不满足前提的记录、旧题来源、历史评分及其余 JSON 转换仍待审查/实施。

SQLAlchemy 当前用于模型元数据和迁移；运行时业务事务仍走统一的 PyMySQL 适配器。

## 演练与升级顺序

1. 确认目标库、MySQL 版本、表结构和 InnoDB 引擎；备份数据库、应用版本和环境配置，验证备份可恢复。
2. 在独立副本加载连接配置。`.env` 不会自动加载：
   ```bash
   set -a; . ./.env; set +a
   python -m flask --app app audit-legacy --output legacy-audit.json
   ```
   审计只读；异常不能直接忽略或自动修复。它不代替迁移对排序规则和列结构的预检。
3. 在副本执行显式升级：
   ```bash
   python -m alembic upgrade head
   python -m alembic current
   ```
   预期版本为 `0008_list_indexes`。核对数量、Rating、历史 JSON、已有版本、回执、快照、参赛和答案行均未变化。从原始旧库升级时新增的词典归属/名称快照为 NULL、版本基线/题目模式为 0；已存在的这些字段保留原值。`0005` 新增成员模式 0/count NULL，`0006` 新增答案模式 0/count NULL；`0007` 新增结算模式 0、用户最新流水引用 NULL。对应新表为空，不自动转换已完成历史。`0008` 只加索引，核对其字段顺序/ASC-DESC/可见性及所有业务数据未变；副本还需评估构建/写入代价、临时空间、已有自定义索引冗余和已知搜索退化，不能只检查版本号。

   参赛数据转换另按 [成员转换流程](GAME_PARTICIPANTS.md#默认只读的单局转换)，旧答案另按 [受限答案转换流程](ANSWER_CONVERSION.md) 审查、备份、确认各自版本后执行。答案工具不创建父关系或推测原题/评分；不能把结构迁移通过或 `ready` 报告视为所有历史数据已转换或全局无异常。
4. 如需创建管理员，使用新用户名并交互输入密码，不通过参数或 SQL 保存明文密码：
   ```bash
   python -m flask --app app create-admin your-admin-name
   ```
   已存在的用户名不会被覆盖或自动提升权限。
5. 先在仓库根目录运行 `npm --prefix frontend ci` 和 `npm --prefix frontend run build`，交付对应的 `frontend/dist/` 后再启动新版本（见 [前端指南](FRONTEND.md)）。完成登录升级、退出、改密、封禁/恢复、管理员重置、词典越权和 CSV 流程；验证 HTTP / Socket 失效会话均不能继续操作。运行 MySQL 集成测试只能使用专门测试实例，见 [基线文档](BASELINE.md#测试与限制)。
6. 副本验证与恢复演练通过后，另行安排正式维护窗口：停止所有旧应用写入、重新备份、迁移、部署新前后端、冒烟验证，再开放服务。不能让旧应用与新结构混合写入，旧写入可能不推进版本、仍按动态词典判题、把已归档的成员 JSON 当作当前状态或将新局空结果 JSON 当作未作答，也会继续写评分 JSON 而忽略新流水/指针，破坏新协议。

## 回滚限制

MySQL DDL 会隐式提交，**不能承诺迁移异常后整体自动回滚**。失败后保留错误和版本信息，检查部分结构；不要反复执行升级或使用 `stamp head` 跳过检查。恢复已验证备份，或人工确认状态后编写修复迁移。

`0008 → 0007` 允许受控的**仅索引降级**：先核对两索引完整定义及可见外键依赖，再删除这两个索引，须部署匹配的 0007 应用；该过程也可能部分提交。它不删除/恢复任何业务记录，不代表开放写入后的数据回滚。详细操作限制见 [索引级降级](LIST_INDEXES.md#仅索引级的受控降级)。readiness 仅校验版本，不代替失败后的实际结构检查。

不支持离线 SQL 生成，因为升级依赖在线结构/数据预检。0001–0007 仍拒绝破坏性 downgrade：scrypt 无法反推旧 SHA-256，删除请求记录会丢失幂等保证，删除快照会丢失原题，删除参赛关系会丢失当前成员/顺序，删除答案会丢失已接受的答题与实际随机评分，删除结算/流水会丢失评分历史及防重证据；不能仅回退应用、清空这些表/指针或把模式改回 0，成员/结果/评分 JSON 不再代表新写入状态。恢复须使用匹配的数据库备份和应用版本；开放写入后，新增用户、词典、对局及改密等数据需有独立保留/重放方案。

## 会话、配置与维护

- 使用稳定、随机的 `WM_SECRET_KEY`。未配置时仅为开发生成临时密钥并告警；重启会使匿名 CSRF 及限流键失去连续性，不适合持久部署。
- 默认会话固定有效期 7 天；登出撤销当前会话，改密/管理员重置/封禁/恢复撤销目标用户所有会话。服务端保存 token 摘要，不保存原始 token。
- 旧 `uid/pwhash` Cookie 和认证参数不再生效；客户端必须重新使用用户名与密码登录。旧 `/api/verify` 已移除。
- 新密码为 6–128 字符，保留首尾空白；登录/当前密码输入允许最多 4096 字符以兼容较长旧密码。旧 SHA-256 验证仍按旧规则去除首尾空白，升级保存其规范化密码；升级后按新密码的精确匹配规则验证。
- 默认 300 秒固定窗口：登录每 IP 30 次、每账户 10 次，注册每 IP 10 次；成功、失败尝试都计数。账户别名按实际 MySQL 排序规则归入同一桶，桶键使用 HMAC，不存明文 IP 或用户名。返回 429 和 `Retry-After`。
- 可周期运行 `python -m flask --app app purge-auth`，仅删除过期会话和过期限流桶，不动业务数据。
- 生产 Cookie 为 HttpOnly、Secure、SameSite=Lax，必须使用 HTTPS。当前不自动信任 `X-Forwarded-For/Proto/Host`；TLS 终止、同源校验及可信代理范围需在部署阶段明确配置。
- 会话和限流状态在 MySQL，Socket 房间/连接撤销通知仍在进程内。当前实时部署只支持单进程多线程，不应直接启动多个独立 worker；多进程广播和生产服务器配置尚未验收。
