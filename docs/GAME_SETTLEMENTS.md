# 结算与评分流水

> 当前另已接入 `0010_rating_events`：比赛评分仍是来源事实，但有事件头的账户以 `rating_event_id` 验证余额链，`rating_ledger_id` 是最近比赛来源投影；两者与余额同事务更新。完整新增规则和人工调分尚未开放的边界见 [统一流水阶段说明](RATING_EVENTS.md)。下文保留 0007 的基础设计与当批证据，不应把旧指针说明理解为可绕过事件链。

此前交付 `0007_game_settlements` 和 `services/game_settlements.py`。**升级后实际发生的结算统一写关系表，包括尚未结束的旧对局；已经完成的历史结算不转换、不重算。** `legacy-v1` 的 Perf/Rating 公式不变，HTTP/Socket 仍共用事务和原回执。

## 表与唯一来源

- `game.settlement_mode`：非空整数、CHECK 0/1、迁移默认 0。新创建为 1。升级前未结束的对局在正常结算命令提交时切换为 1；升级前已结束的局保持 0，重复结束不创建流水。它独立于题目/成员/答案模式，不会转换这些数据。
- `game_settlement`：`game_id` 主键并 RESTRICT 引用 `game`，一局只能有一份结算；`rated_count` 为非负整数，记录实际计分人数；保存 `rating_version`、`settled_at/recorded_at`。**零答案结束也有结算头，人数为 0，没有评分行。**
- `game_rating`：BIGINT 自增主键 `id`，`(game_id,user_id)` 唯一；RESTRICT 外键分别指向结算头及用户。保存实际最终 `perf`（DOUBLE）、`rating_before/rating_after`（signed INT）和 `delta`（BIGINT）。CHECK 保证 `after = before + delta`，整数加法使用 DECIMAL 避免中间溢出，不用 DECIMAL 舍入 Perf。
- `(user_id,id)` 索引用于个人流水读取；对局评分由 `(game_id,user_id)` 索引读取。成员来源可能仍是旧 JSON，因此不伪造参赛行来满足复合外键；服务端仍验证所有评分人都是本局已答题成员。
- `user.rating_ledger_id`：可空 BIGINT、索引及到 `game_rating.id` 的 RESTRICT 外键。迁移默认 NULL，不为历史评分制造流水。新结算更新余额时一起指向该用户的最新行；读取/结算验证引用归属和余额，不把 FK 当作所有业务校验。

`user.rating` 仍是当前余额，登录/公开资料/排行榜的字段和读取方式不变。新结算不再写 `user.ratinghistory` 或 `game.perf/ratingdelta`；旧值原样保留，新局这些 JSON 为空。`user.gamehistory` 仍按原规则记录实际作答过的游戏，用于前五场基线；它和 `wordlist` 等剩余 JSON 尚未转换。

模式 1 读取验证：未结束不能有结算，结束必须有结算头；人数与实际答题者及评分行数一致；每人只出现一次、Perf 与其最后答案一致、分数有限、整数范围/加法、规则版本及时间有效。损坏返回 **`invalid_game_settlement / 409`**，不回退旧 JSON 或用当前 Rating 补造历史结算。计算的新 Rating 超出 signed INT 范围时返回 `rating_out_of_range / 409`，整个命令回滚。

## 原子提交与锁

1. 预留请求 ID，锁对局，校验版本、状态及权限。
2. 按用户 ID 升序取得全部参赛用户排他锁；从实际答案提取最终 Perf，仍只调用 `rating_delta()` 计算一次。未答题用户不更新余额、指针或历史；答过题但增量为 0 的用户仍有一条结算流水。
3. 通过**锁定用户行的最新流水指针**按主键 `FOR SHARE` 当前读，验证结算前余额。不能依赖早于等待用户锁建立的 MVCC 视图；不能 JOIN 加锁其他对局，避免“用户 → 另一对局”锁倒置。
4. 没有指针就不查询空流水范围。对空的 `(user_id,id)` 范围做锁定扫描可能使两个无共同用户的首次结算互相持有 gap lock；已有主键引用避免此路径。
5. 插入结算头、评分行，再更新余额和最新指针，最后更新对局状态/来源。与最终答案、答案数量、用户游戏历史、版本及成功回执同事务提交。最后一题自动结算仍只增加一次版本；任一步失败全部回滚。
6. 提交后才广播。相同请求 ID 重放原回执，不重算、不重写时间；新结束请求在有效已结束状态下返回 `already_finished=true`。

评分外键检查发生在有序用户锁之后；不会在取得所有评分用户排他锁之前先插入含用户 FK 的流水。结算头保证空结算也只发生一次，评分唯一键提供每局每人防重，但二者都不代替事务锁、授权或状态校验。

## 历史展示与时间

对局状态的 `userrating` 结构不变：每人返回 `ratinghistory`，条目仍为 `game_id/delta/new_rating`。读取边界保留旧 JSON 前缀的内容/顺序，再追加新流水；新条目不暴露数据库主键、指针或时间。旧 JSON 的非法游戏 ID、重复记录、与新流水重叠，以及新流水余额链/最新指针不符都要求审查，不自动去重、推测或修复。旧记录额外字段保留，不从今天的 Rating 重建过去的基线。余额链校验针对新流水及当前余额，不猜测旧 JSON 缺失的结算前值，也不代表旧历史余额链已经审计通过。

新流水按自增 ID 读取。对同一个用户，用户锁确保后续结算只能在前次提交后分配 ID，因而反映该用户的结算顺序；不按对局创建 ID 或墙钟排序。ID 可有回滚空洞，**不是全站提交时序或可恢复所有历史的事件编号**。

新结算的两个时间字段为 UTC 微秒写入时点，不承诺网络提交时刻/事务提交时刻。`settled_at` 可空以表达未来显式转换时未知的历史时间；正常新结算写入始终有值，也没有猜测旧时间。状态与用户历史在同一只读事务快照中读取，另一局同时结算不会把旧余额与新流水混在一个响应中；另一局变化仍不推进本局版本。

这是只追加的应用接口，不是 DBA 防篡改系统：没有防特权 SQL 改写的触发器，无法识别所有形状合法的篡改。读取验证不重新计算历史 Rating 公式。建议运行账号对两张新表仅有 SELECT/INSERT，用户余额/指针仍需 UPDATE，迁移使用独立账号。

## 迁移、审计与回滚

本文对应 `0007_game_settlements`；当前 head/readiness 以 [迁移指南](AUTH_MIGRATION.md) 为准。结算迁移 DDL 前检查同名/部分表、列、约束和索引冲突、signed INT 用户/对局主键及 Rating 类型、旧评分列可空和 InnoDB。升级只增加结构、模式 0、指针 NULL；旧业务值、Rating、历史 JSON、版本、回执、快照、成员和答案全部保留。不会给已结束对局插入结算头或流水。

`audit-legacy` 兼容迁移前结构，识别结算缺失/异常、孤立用户/对局/结算引用、跨 JSON/流水重复、余额链和最新指针异常；报告只有实体 ID/问题类型，不输出答案、用户资料或评分内容。没有执行真实旧库审计/转换。

已另提供 [受限旧答案转换工具](ANSWER_CONVERSION.md)，它保留实际答案分数并检查已有关系结算，但不修改结算、余额、指针或历史评分 JSON。

**这不是历史评分 JSON 转换工具。** 不能手工把旧历史复制到新表然后留着原 JSON，否则重复且新流水顺序不再代表未来结算顺序；后续转换须显式设计来源/顺序、审查和版本确认，保留历史证据，不重算或补造数据。

升级前停止旧写入、备份并在授权副本演练，见 [迁移指南](AUTH_MIGRATION.md)。旧应用会继续写 JSON、忽略最新指针，不能与新应用混写。MySQL DDL 可能部分提交；失败后检查/恢复，不能 `stamp head` 跳过。拒绝破坏性 downgrade；不能仅回退代码、清空流水/指针或把模式改 0。恢复需匹配备份/应用，并处理开放写入后新增数据。

## 验证边界

结算批次的 32 项真实 MySQL 用例及既有回归覆盖：HTTP/Socket 结算和重放、应用重建、空结算/零增量/未答题、旧历史保留与旧未结束局的新结算、顺序及精度、答题/结束竞争、跨局评分、不同用户首次结算、等待锁后的当前读、只读一致快照、五个写入阶段回滚、范围/版本耗尽、唯一键/FK/CHECK、损坏拒绝、审计和迁移预检。9 项关键并发/回滚用例连续三轮通过。

全部使用隔离 MySQL 和合成数据。历史转换、授权副本/恢复演练和生产规模性能仍未验收；本批 [Vue 播放页](GAME_PLAYING_UI.md) 已通过独立真实 MySQL/Chromium 双用户关键流程及 SQL 一次性结算核对，不代替所有故障、权限或生产验收。对局历史接口仍读取相关用户的全部历史，不承诺长期流水增长后的响应成本恒定。
