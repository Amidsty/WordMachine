## 方法与可复现边界

- 三档增量合成规模如下，另有原夹具 3 用户、1 词典、3 单词、1 对局；完整实际行数写入报告。

  | 档位 | 用户 | 词典 | 单词 | 对局 |
  |---|---:|---:|---:|---:|
  | smoke | 200 | 40 | 1,000 | 120 |
  | medium | 20,000 | 1,000 | 100,000 | 10,000 |
  | large | 100,000 | 5,000 | 500,000 | 50,000 |

- 单词一半集中在一个热点词典，其余分散；包含软删除、NULL 删除标记/名称/Rating、同分、稀疏 `needle` 及字面 `%_!`；负分另由独立 MySQL 回归覆盖。对局混用旧 JSON 和规范成员/快照，含等待、进行、取消；观察者与成员都覆盖。没有巨型答案/评分历史负载。
- 22 个服务场景：词典首/末/100 条页、包含搜索及未命中；热点词典单词首/末页、包含/字面符号/未命中；用户首/末页、包含/未命中；排行榜首/末页；大厅首/末页、等待、来源名称搜索、未命中与筛选外活动对局定位。末页通过 `page=1000000` 收敛，保留真实大 OFFSET。
- 真实调用现有服务、PyMySQL 和 MySQL；记录实际执行的 SQL/绑定参数，不复制另一套查询实现。每个服务调用建立新的连接；测量前在合成库执行一次 `ANALYZE TABLE`，不在应用读取中执行。
- 测量调用与预热都使用只读事务，记录器拒绝非 SELECT 和批量写。真实 MySQL 用例另绕过 Python 记录器验证 DML 被 1792 拒绝。它是受控测试工具，不是任意 SQL 的安全沙箱。
- `service_ms` 是客户端完整服务耗时，包含连接、DTO 处理及只读/会话计数采集开销，**不含 HTTP、认证、浏览器或队列时间**。`execute_ms` 是缓冲游标 execute 的客户端耗时，包含服务端执行及结果传输，不是服务端 CPU 时间。
- 保存原始采样、最小/中位/最大值、SQL 数量及返回行数、各连接 `Handler_read_*` 增量。Handler 是引擎访问操作计数，可能包含索引/临时表操作，不能直接当成扫描业务行数或跨版本比较。
- 保存 `EXPLAIN FORMAT=JSON` **估算计划**，不是 `EXPLAIN ANALYZE` 的实际循环数或独立耗时证明；计划采集不在计时区间。优化器可随统计信息、版本及数据分布选择不同计划，测试不强制某个索引/成本数字。
- 保存 MySQL/Python 版本、缓冲池、排序规则、隔离级别、优化器开关、逻辑 CPU 数、迁移 head、实际行数和相关应用源文件 SHA-256。报告只有合成查询/数据参数，不保存 Cookie、密码、会话摘要或连接 URL；仍按测试产物保存。
- 每场景重复读取必须得到相同结果摘要、SQL/绑定参数及返回行数；另核对关键总数与活动对局。比较工具要求场景集合、方法、记录的环境/行数一致，并逐项核对完整结果 SHA-256、分页、ID 和活动对局，再展示耗时。不保证摘要一致就等于完整业务证明，业务边界另有回归。
- 串行调用，每场景一次预热；不清空操作系统缓存，不保证整个数据集已驻留缓冲池，宿主机也非独占。**不是冷启动、并发吞吐、写竞争或线上容量测试**；不使用易抖动的毫秒断言决定测试成败。

## 三处优化及语义保护

### 词典：分页后一次汇总本页单词数

`wm_app/services/dictionary.py:list_dictionaries()` 原先在 SELECT 中对每个词典执行相关计数子查询。当时 0007 的合成结构没有 `word.dictid` 索引，执行计划显示每行计数重扫单词表。

现在同一个 `reading()` / REPEATABLE READ 事务内执行：精确词典 COUNT → 原排序 LIMIT/OFFSET 页 → 本页至多 100 个 ID 的单次 `GROUP BY dictid` 计数。非空页固定三条 SQL，不是每行一条；空页不发 `IN ()`。没有缓存或近似计数，没有把全部单词搬入 Python。

计数仍只含 `word.deleted=0`，空词典为 0，NULL/软删除标记不当作活跃；名称、归属、权限和排序不变。独立真实连接在页读出后提交改名/归属/单词删增，后续计数仍看到原快照；下一次读取才看到新值。

**剩余成本：**无合适索引时仍扫描一次单词表，GROUP BY 可能使用临时表；“仅汇总本页”不等于存储引擎只读取本页相关行。

### 排行榜：一次有界读取代替全量 COUNT

`leaderboard.py:list_leaders()` 一次读取 `deleted=0 ORDER BY rating DESC, id ASC LIMIT 100`，用这至多 100 条的长度得到公开榜单精确总数，再切出请求页与全局名次。可能比原小页多传回一些公开字段，但不会把所有用户读到 Python。

保留 top 100、越界收敛、NULL/负数/同分排序及空表语义，不泄露私有字段。**没有评分排序索引时仍需扫描/排序活跃候选**，LIMIT 不意味着 O(100) 的数据库成本。

### 大厅：无名称搜索的计数不关联词典

`lobby.py:list_games()` 无 q 时精确 COUNT 只读 game；字典主键 LEFT JOIN 在这里不能筛掉任何对局。名称搜索仍用原快照/旧名称 CASE 和 LEFT JOIN；页读取、成员批量加载与活动对局查找不变。

缺失/已删词典、NULL 名称、快照名称及筛选外活动对局均有真实 MySQL 回归，不把缺词典的历史局从数量中移除。

## 本机测量记录

MySQL `8.0.42-0ubuntu0.20.04.1`，Python `3.11.17`，Linux x86-64 / 6 逻辑 CPU，InnoDB 缓冲池 **64 MiB**，`utf8mb4_0900_ai_ci`、REPEATABLE READ，performance_schema 关闭；七版迁移不变。这不是生产配置建议。

medium 实际为 20,003 用户、1,001 词典、100,003 单词、10,001 对局、13,332 成员、6,666 快照题。修改前/后的 22 个场景完整结果摘要全部一致；每项一次预热、3 次测量，中位毫秒：

| 场景 | 修改前 | 修改后 | 独立复跑修改后 |
|---|---:|---:|---:|
| 词典首 20 条 | 378.49 | 24.33 | 26.26 |
| 词典末页 | 330.30 | 31.32 | 32.94 |
| 词典 100 条页 | 1869.36 | 25.19 | 26.78 |
| 词典包含搜索 | 220.27 | 32.12 | 32.51 |
| 排行榜首页 | 13.10 | 9.23 | 9.75 |
| 大厅无搜索首页 | 11.70 | 5.53 | 5.38 |

相关证据：词典首页 `Handler_read_rnd_next` 中位从 2,001,082 降到 101,027，100 条页从 10,001,402 降到 101,107；SQL 数从 2 增至 3，但消除了按页行数重复的全表计数。排行榜 SQL 2→1，计划仍有 filesort；大厅无搜索 COUNT 改为覆盖索引扫描，不再逐局关联词典。包含搜索/单词/管理员用户读取未做改写，不将其小幅时延波动计作优化收益。

large 档修改后另运行两次，22 个结果摘要也一致。最后一次热点词典单词末页约 **225 ms**、未命中约 **370 ms**；词典 100 条页约 **115 ms**、大厅名称未命中约 **116 ms**。这些增长说明全表扫描、精确计数、包含搜索及 OFFSET 的规模成本仍在，不能把 medium 的改善外推成生产容量。large 没有修改前测量，不声称该档改善倍率。

本次原始报告保存于 `/tmp/wm-lists-before.json`、`/tmp/wm-lists-after.json`、`/tmp/wm-lists-repeat.json`、`/tmp/wm-lists-large.json`、`/tmp/wm-lists-large-final.json`；这些是本机临时产物，不是仓库依赖或 CI 成果。后续执行应保存自己的报告，重测时延而非照抄本表。
