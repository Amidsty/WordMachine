# 列表索引、分页取行与显式迁移

**本文记录 0008 索引批次的实现、迁移规则及当时的 22 场景/740 测试证据。** 后续 N1 已扩为 34 场景并调整搜索/首页 SQL，最新结果与剩余退化见 [N1 记录](LIST_SEARCH_READS.md)，下表不替换成后续数据。索引迁移规则仍适用；使用当前代码重跑下面命令，不会自动还原当时的 SQL/场景。

该批接续 [第一批查询优化](LIST_PERFORMANCE.md)。当前 head/readiness 为 **`0008_list_indexes`**。只在隔离合成 MySQL 验证，**未迁移业务库；生产性能未验收**。索引有读、写及空间代价，不是所有查询都会变快。

## 改动范围

新增 [`0008_list_indexes.py`](../migrations/versions/0008_list_indexes.py)，依赖 `0007_game_settlements`，不修改 0001–0007：

| 表 | 非唯一、可见 BTREE 索引 | 目的 |
|---|---|---|
| word | `ix_word_dict_deleted_id (dictid, deleted, id)` | 词典范围内的活跃单词计数、按 ID 分页及本页词典汇总 |
| user | `ix_user_deleted_rating_id (deleted, rating DESC, id)` | 活跃用户 top 100 的评分/同分顺序，避免榜单全表排序 |

同步 SQLAlchemy 元数据，不改变字段、外键、唯一约束或业务数据。没有新增 game 索引、全文索引、缓存、近似 COUNT、游标分页或索引强制提示。其他既有/自定义索引不自动删除、改名或收编；副本审查需排查等价冗余与写放大。

`dictionary.get_words()`、`auth.list_users()` 改为一条 SQL 内的 **ID 子查询分页 → 主键读取本页字段 → 原顺序输出**。LIMIT 阻止派生表合并，避免为大 OFFSET 跳过的每条记录都经二级索引取出完整字段。包含搜索仍可能读取被跳过条目的文本，OFFSET 也仍需扫描/排序候选，不是恒定成本。

精确 COUNT 为 0 时不再执行第二次页查询；单词仍先验证词典可读，用户仍先验证 root。计数、ID 页与字段读取保持原 REPEATABLE READ 快照，参数仍绑定，字面包含搜索、页码收敛、NULL、软删除和公开字段契约不变。没有改变任何业务写协议、判题、评分、HTTP/Socket 幂等或历史转换。

## 迁移、等待与失败边界

迁移必须显式执行，应用启动、普通读取不创建/调整索引。迁移前按 [通用指南](AUTH_MIGRATION.md) 完成授权、备份、副本及恢复演练，并安排维护窗口；不能直接用本地测试结论上线。

- **先检查两张表，再做第一条 DDL**：InnoDB、id 主键、预期 signed INT/TINYINT 列，以及大小写不敏感的目标索引名。即使同名索引定义完全一致，也不跳过或收编；部分升级/自定义结构必须审查。
- 两张表分别 `ALTER TABLE ... ADD INDEX ..., ALGORITHM=INPLACE, LOCK=NONE`；不允许静默回退 COPY 或更强锁。INPLACE 不等于零工作量，索引构建仍要读数据、占空间并维护并发变更。
- **LOCK=NONE 仍需要元数据锁**。迁移在自己的连接内把每次元数据锁等待限制为 `min(原 lock_wait_timeout, 30 秒)`，不放宽原来更短的限制；结束/失败后恢复原值，连接已失效则不为重置它而重连。不修改全局设置或应用连接配置。这不是索引构建总时长的超时上限，也不保证等待期间不影响其他请求。
- MySQL DDL 可隐式提交：第一张表已建索引、第二张表失败时，第一条不会自动回滚，版本仍可能停在 0007。确认丢失也不能当作回滚；重试会因部分结构拒绝。必须保持维护状态、检查实际结构及版本，审查后恢复/修复再继续，**不能 `stamp head` 或盲目重跑**。
- readiness 只校验版本，不逐个证明实际索引/约束完整。尤其部分 downgrade 后版本可能仍为 0008；不能仅凭 readiness 宣布恢复成功。预检也不能消除并发 DDL、不可见跨库约束、磁盘不足或连接故障，迁移账号须能审查相关结构及外键。

### 仅索引级的受控降级

0008 支持回到 0007，**只删除本次两个索引**，不删除业务记录/关系、不重置模式/余额/回执。两索引的列顺序、ASC/DESC、非唯一、完整键、BTREE、可见性均核对成功后才执行第一条 DROP；缺失/自定义形状拒绝。对以这些列前缀为本地或被引用键的可见外键保守拒绝，即使另有索引也不擅自判断可删除。

MySQL 对非唯一被引用索引可能给出 NULL `UNIQUE_CONSTRAINT_NAME`，因此预检通过 `KEY_COLUMN_USAGE` 的有序被引用列识别依赖，不靠该名称猜测。此情况有真实 MySQL 回归。

仅在授权、备份和演练后，按确认的恢复方案执行：

```bash
python -m alembic downgrade 0007_game_settlements
python -m alembic current
```

须部署与 0007 匹配的应用；当前应用 readiness 会返回 503。0001–0007 的破坏性降级仍拒绝，0008 的索引降级不是历史数据回滚，更不解决开放写入后的增量恢复。DROP 同样可能部分提交或等待元数据锁；失败后不能假设两索引都已删除。

## 基准扩展与复现

沿用 `tests/performance/` 的 22 个实际服务读场景、三档确定性数据和结果摘要。新增：

- `--list-perf-revision=0007_game_settlements`：只在新建合成库停在索引前版本；默认 `head`。仍使用**当前应用 SQL**，不是自动还原旧应用，不用于部署。
- 报告 `storage`：记录 word/user 的索引定义以及 `information_schema.TABLES` 的 DATA_LENGTH/INDEX_LENGTH。空间是统计/分配估算，INDEX_LENGTH 为整表全部二级索引，不是精确逐索引有效载荷；不额外授予读取系统库索引统计的权限。
- `--list-perf-write-costs`：明确开启两个已提交写探针：真实词典服务导入 **5000 行 CSV**，以及 **100 个合成用户**的顺序主键 Rating UPDATE。后者只测索引维护，**不是对局评分公式或结算性能**。每项一次预热，采样次数与读场景一致，计时包含提交、不含准备/核对/清理。
- 探针只接受 testing 配置及随机测试库命名，且依赖合成夹具；不提供任意业务库入口。临时词典/单词及合成评分在 finally 清理/恢复；随后核对行数及全部 22 个公开读取摘要。实际 MySQL 用例另比较全部业务表原始行，验证 NULL、历史、余额、字段均未改变。测试库整体仍由原夹具清理。保护检查不是指向生产实例的授权。
- 比较报告默认仍拒绝环境/版本变化。只有显式传入 **`--revisions BEFORE AFTER`**，且报告版本恰好匹配这一对时，才允许该版本差异；其他环境、规模和结果校验不放宽。比较表仅比较读场景，写探针与空间在报告中单独审查。

```bash
# 路径必须不存在；全部自动使用新私有 MySQL，不使用继承的业务库配置
make benchmark-mysql PERF_ARGS='--list-perf-size=medium --list-perf-runs=3 --list-perf-revision=0007_game_settlements --list-perf-write-costs --list-perf-report=/tmp/index-before-new.json'
make benchmark-mysql PERF_ARGS='--list-perf-size=medium --list-perf-runs=3 --list-perf-write-costs --list-perf-report=/tmp/index-after-new.json'
.venv/bin/python -m tests.performance.compare /tmp/index-before-new.json /tmp/index-after-new.json --revisions 0007_game_settlements 0008_list_indexes
```

large 可用同样方法，文件另取新名。CI 既有 smoke/1 入口在本地重新验证，但没有实际 CI 执行结果；可选写探针不改变默认只读基准，常规回归中另有探针数据恢复测试。

## 实测收益与明确退化

本机 MySQL 8.0.42、Python 3.11.17、6 逻辑 CPU、64 MiB InnoDB 缓冲池、utf8mb4_0900_ai_ci、REPEATABLE READ；非专用宿主机。每场景预热一次、测量三次。下表 **0007 与 0008 均使用本批 ID 分页/零计数短路 SQL**，隔离观察增加索引后的差异，不能与第一批旧 SQL 耗时混算收益。两档各 22 个完整结果摘要一致，写探针后再次核对也一致。

| 场景，中位 ms | medium 0007→0008 | large 0007→0008 |
|---|---:|---:|
| 词典首 20 条 | 25.93→4.00 | 121.47→4.09 |
| 词典 100 条页 | 27.62→5.58 | 123.07→5.91 |
| 热点单词末页 | 42.99→18.46 | 208.99→80.13 |
| 排行榜首页 | 9.46→2.92 | 36.95→2.59 |
| 用户末页 | 11.38→10.61 | 44.74→43.23 |
| **用户首页** | **5.97→8.60** | **20.26→33.03** |
| **热点单词包含搜索** | **37.18→47.52** | **172.69→361.59** |
| **热点单词字面符号搜索** | **38.39→48.21** | **172.93→382.63** |
| **热点单词未命中** | **35.18→44.71** | **168.92→313.26** |

- 计划显示词典计数可用范围/覆盖索引，榜单用评分顺序索引而不再 filesort。
- **退化不是噪声被忽略的成功项**：热点词典占一半单词，`%q%` 不能靠本次 BTree 定位文本，优化器选择二级索引后要大量回表；用户首页也可能选择评分索引再按 ID 排序。索引不保证优化器在所有选择率/缓存条件下取最优计划，未强制索引或更改搜索语义。
- 初次只加索引时用户末页约 12→27 ms，ID 分页使其回到约 10–11 ms；精确零计数短路也消除了未命中的第二次相同扫描。另测试了第三个 `(deleted,id)` 用户索引，medium 样本没有明显额外收益，因此**未纳入迁移**；不据此断言所有生产分布都不需要它。
- 本批交付的是有证据及代价记录的索引/查询方案，不是全场景性能验收。热点包含搜索、用户列表计划、极端删除比例、冷缓存、写竞争与并发负载仍待优化/评估，不能只摘取最快一行宣布整体改善。

写探针中位 ms（采样很少，不据此承诺固定增幅）：

| 已提交探针 | medium 0007→0008 | large 0007→0008 |
|---|---:|---:|
| 5000 行实际 CSV 导入 | 381.12→402.95 | 387.52→570.38 |
| 100 行合成 Rating UPDATE | 11.48→11.73 | 9.98→14.43 |

large 中 CSV 原始范围约 372–404→427–584 ms；Rating 原始范围约 9.76–38.72→11.39–18.60 ms，提交/I/O 波动明显。新增二级索引需要维护，不宣称写入免费。空间估算：medium 的 word INDEX_LENGTH 增加约 **2.52 MiB**、user 约 **0.48 MiB**；large 分别约 **10.52 MiB / 2.52 MiB**。这不是生产磁盘预留值，构建临时空间、日志和实际字段长度另需评估。

本机报告：`/tmp/wm-index-medium-0007.json`、`/tmp/wm-index-medium-0008.json`、`/tmp/wm-index-large-0007.json`、`/tmp/wm-index-large-0008.json`。临时文件不是仓库依赖；后续应保留自己的报告。估算 EXPLAIN、客户端计时、Handler 计数、串行预热及其他限制仍见 [基准方法](LIST_PERFORMANCE.md#方法与可复现边界)。

## 回归与验收范围

新增 **21 项单元 + 31 项真实 MySQL 回归**，包括：

- 升级/索引降级/再升级保留所有业务行、会话/限流、旧 JSON 原文、答案、结算、余额/指针、版本及回执，已有会话有效、原请求仍重放；空库完整升级。
- 元数据与真实索引方向/非唯一/可见/完整键一致；大小写同名、完整同名、错误类型/引擎/主键在第一条 DDL 前拒绝。
- 缺失、ASC/DESC 不符、不可见、唯一/函数索引及本地/被引用外键阻止降级。注入第二条 ADD/DROP 失败，以及真实元数据锁等待超时，验证部分 DDL 保留、版本不假推进、重试拒绝；三项失败/等待用例独立复跑通过。
- 两个真实连接在 COUNT 后提交删改/新增，ID 页/字段仍看到原快照，零计数不会读到新插入；基准只接受明确版本对、其余环境变化仍拒绝；写探针恢复全部行。

完整回归 **740 Python（509 unit + 231 MySQL）、156 Vitest**，98 个 Python 文件静态检查、前端 lint/格式/类型/构建通过；13 个模拟 API 浏览器检查、5 个真实 Chromium 场景及 4 项独立编排/SQL 核对通过。基准仍为每次 1 项编排/22 个读场景，两个写探针与重复采样不混成常规测试数量。

真实旧数据副本、生产数据分布与硬件、延迟/吞吐目标、备份恢复和上线仍独立待验收；阶段 3/4 和上线不能据此勾选完成。
