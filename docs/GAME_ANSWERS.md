# 新对局答题记录

此前完成新对局的规范化答题存储与 `0006_game_answers`；现已接入 [未来结算流水](GAME_SETTLEMENTS.md)。现另提供 [受限旧答案显式转换工具](ANSWER_CONVERSION.md)，不是通用历史恢复器；历史评分及其余 JSON 转换仍未完成。保留 `legacy-v1`、同一套权限/轮次规则、请求幂等和结算事务。没有迁移业务库或重算历史评分。

## 唯一来源与约束

- `game.answer_mode`：非空、默认 0。0 使用旧 `game.result` JSON；新创建显式为 1，`result=NULL`，不双写结果 JSON。
- `game.answer_count`：模式 0 必须 NULL；模式 1 显式非 NULL、非负，并要求 `question_mode=1`、`participant_mode=1`。数量只校验完整性，不是答案内容来源。
- `game_answer`：`(game_id, position)` 主键，即一局一个题序只能有一条已接受答案；位置从 0 开始。不是按用户唯一，同一人可回答多轮。
- `(game_id, position)` RESTRICT 外键指向 `game_question`；`(game_id, user_id)` RESTRICT 外键指向 `game_participant`。不能引用其他局的题目或非本局成员。对局/用户引用由这两张父表继续约束。
- 不重复存储 `word_id`：协议中的来源单词 ID 从已验证的题序清单取出，文本仍由快照提供；源单词删除不影响答题。外键不代替当前轮次、前缀连续性或服务端授权检查。
- `answer` 为 UTF-8 TEXT，保存原有去首尾空白/小写后的有效答案。保留输入最长 255 字符的限制；Unicode 小写可能扩展长度，因此不能使用 VARCHAR(255) 保存规范化结果。非法 Unicode 在业务连接前拒绝。
- `correct` 只允许 0/1；`usercombo/globalcombo` 为非负整数；保存当时实际的 `perf_delta/perf/rating_version`。两个评分数值使用 MySQL **DOUBLE**，与 Python binary64 一致，不改成低精度 FLOAT 或舍入的 DECIMAL，不重新抽随机数或重新判题。
- `answered_at/recorded_at` 为 UTC 微秒写入时间；新答案两者同时赋值，不声称是客户端提交时点或事务提交时间。`answered_at` 可空以表达未知历史时间，显式转换旧答案时为 NULL，不补造历史时间。
- `(game_id, user_id, position)` 索引覆盖成员外键和局内个人答题查询；全部答案按主键题序读取。

`game_answers.py` 只适配两种存储，向原服务提供同一个有序 `result` 列表。模式 1 从不解析或回退 `result` 存档，即使存档是坏 JSON。读取时验证数量、连续已完成前缀、题目范围、成员轮次、状态、文本、分数有限性及版本/时间类型；损坏返回 **`invalid_game_answers / 409`**，不猜测缺失记录。不会因为坏数据而提前公开未来英文答案。

这些检查不是对特权 SQL 的完整防篡改或评分数学证明；能通过形状检查的人工改分仍可能存在。没有防 DBA 改写的触发器。应用无编辑/删除答案接口，建议运行账号对答题表仅有 SELECT/INSERT，迁移使用独立账号。

## 事务与评分

1. 预留请求 ID，再取得对局排他锁、校验版本，加载权威的成员、题目和答案。
2. 共享服务验证状态、当前用户和题目；按用户 ID 升序取得全部评分用户排他锁。
3. 仍由 `score_answer()` 执行唯一一份 `legacy-v1` 计算；插入本轮答案，仅更新 `answer_count`，不重写历史答案行或时间。
4. 更新用户游戏历史；最后一题还在同一事务结算。答案、数量、评分/历史、版本和成功回执统一提交，任何异常全部回滚。最后一题仍只推进一次版本。
5. 提交后广播；通知失败不能撤销已提交答案，客户端通过读取/轮询恢复。

答案外键检查发生在有序用户锁之后，不改变原锁顺序；参赛顺序即使相反，跨局评分也按用户 ID 升序锁定。请求重放发生在轮次检查前，返回原成功回执，不再次插入、随机评分或更新时间。原回执可以早于当前状态，也不表示损坏的关系已经修复。

答错仍按旧规则从 Rating 基线重新计算 Perf，而不是从上次 Perf 扣减；提前结束时未答题用户不改 Rating，未答题英文仍隐藏。`user.gamehistory` 仍写 JSON；旧 `game.perf/ratingdelta`、`user.ratinghistory` 保留作历史来源，新结算已由独立关系表接管，不双写。答题轮次主键不能代替结算头及每局每人评分的唯一约束，详见 [结算流水指南](GAME_SETTLEMENTS.md)。

HTTP/Socket 的 URL、事件、成功回执和 `result` 字段形状不变；不暴露数据库位置、时间或存储标记。[Vue 播放页](GAME_PLAYING_UI.md) 与 [历史详情](GAME_HISTORY_UI.md) 共用协议，不必维护第二套计分规则；详情不重新判题或计算评分，历史缺失字段明确显示缺失。

## 旧数据与发布

`0006` 仅增加结构。升级前对局全部为 `answer_mode=0/answer_count=NULL`，不读取、修复、转换任何旧答案；旧业务列、版本、成功回执、已有快照和参赛行保持原值。即使某旧局已有快照和参赛关系，也不自动切换答案来源。

未转换对局继续原 JSON 路径，缺失 Perf 仍要求审查，不能推算。`convert-game-participants` 只转换成员，不会转换答案或恢复原题。`convert-game-answers` 默认只读，仅接受已有完整快照/参赛关系和可完整复制的答题字段，应用必须确认版本；保存未知作答时间 NULL，原 `result` 字节保留为不再更新的存档，之后关系为唯一来源。不补造缺失字段、丢弃额外字段或重算评分；拒绝 `legacy_live`，不把今天的词典当作原题。操作、拒绝范围、提交确认丢失及恢复边界见 [转换指南](ANSWER_CONVERSION.md)。没有授权真实副本转换结果。

本文对应 `0006_game_answers`；当前 head/readiness 以 [迁移指南](AUTH_MIGRATION.md) 为准。答题迁移在 DDL 前检查部分结构、大小写不敏感的列/约束名冲突（包括其他表上的同名约束）、父表 signed INT 主键、模式列与可空 `result`、InnoDB。MySQL DDL 可能部分提交，失败后检查/恢复，不能 `stamp head` 跳过。

升级只在确认目标、停旧写入、备份及授权副本演练后执行，见 [迁移指南](AUTH_MIGRATION.md)。禁止旧应用混写：新局 JSON 为空，旧应用可能把它当作尚未作答。拒绝破坏性 downgrade；不能仅回退代码、清空答案表或把模式改回 0，须使用匹配备份并处理开放写入后新增数据。

`audit-legacy` 兼容迁移前结构，模式 1 审查实际关系而非 JSON，报告缺失/异常答案、旧模式意外关系及孤立对局引用。报告仅含实体 ID/问题类型，不输出提交答案、题面或评分内容。

## 验证边界

真实 MySQL 用例覆盖 HTTP/Socket 完整答题至结算、跨传输及应用重建后的原回执、binary64 精度、Unicode 扩展、超过旧结果 TEXT 容量的答题列表、仅追加/时间保留、未来英文隐藏、并发重复答题（有/无请求 ID）、答题/结束竞争、反向成员顺序的跨局最终结算、轮次唯一键/FK/CHECK、损坏拒绝、版本耗尽、多个写入阶段失败回滚，以及迁移预检/原值保留。已有快照、参赛和旧 JSON 用例继续回归。

这些验证只使用隔离 MySQL 与合成数据，不等于授权旧数据转换、备份恢复、生产规模性能或真实数据库双用户浏览器验收。完整成绩展示仍一次读取本局所有答案；关系表解决追加存储，不承诺超长对局的查询/响应成本恒定。
