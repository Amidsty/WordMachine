## 落地的查询变化

### 单词搜索：同一 SQL 内的单行边界聚合

对非空搜索词，在 COUNT 和 ID 分页的来源中使用：

```sql
FROM word
JOIN (
    SELECT MIN(id) AS first_id, MAX(id) AS last_id
    FROM word WHERE dictid = %s AND deleted = 0
) bounds ON id BETWEEN bounds.first_id AND bounds.last_id
WHERE dictid = %s AND deleted = 0
  AND (english LIKE %s ESCAPE '!' OR chinese LIKE %s ESCAPE '!')
```

两处 dictid 均绑定同一服务参数，文本条件保持不变。聚合无 GROUP BY，恰好产生一行，不增加匹配条目或重复计数；空词典的两个边界为 NULL，连接不匹配任何行。signed INT 极值、负数、0、ID 间隙、NULL 文本和软删除均由真实 MySQL 验证。

已有 `(dictid, deleted, id)` 索引可用于寻找范围端点。单行派生表让优化器看到可用的主键范围或词典范围，不强制索引、不读取估算行数来决定业务结果。它也不保证优化器在每种分布下选最优计划，`%q%` 仍需检查文本。

父词典验证、COUNT 与分页保持同一 REPEATABLE READ 快照；COUNT 和分页各自在 SQL 内计算边界，没有跨请求缓存。包含搜索非空结果仍为 **3 条客户端 SELECT**（词典、COUNT、页），零结果为 **2 条**；无搜索的读取完全不加聚合。客户端 SQL 数不变不等于免费：数据库内部仍增加聚合/优化/可能的临时表成本。

### 用户列表：只调整无搜索的第一页

精确 COUNT 后按**收敛后的 offset** 判断：无搜索且 offset=0 时直接选择本页公开字段；搜索页和所有非零 offset 页仍使用原 ID 派生表再取字段。

原因是首页没有需要跳过的条目，原 ID-only 派生表可能让 MySQL 选择覆盖的评分索引，再对全部活跃用户按 ID 排序。直接读取公开字段在常见分布下恢复短的主键倒序读取，但高删除比例下也可能选择代价较高的路径；未设置任意行数阈值、强制索引或自动改优化器配置。

root 校验、include_deleted、字面搜索、NULL、排序、精确 total 和页码收敛不变。COUNT=0 仍直接返回；只选择原有公开字段，不读取密码。请求超出末页、但收敛到第一页时也适用同一规则。

## 候选实验与未采用的方案

- 强制主键扫描：大词典较快，但 50 条左右的小词典搜索从约 0.3 ms 增至约 120 ms，不采用。
- 把 MIN/MAX 写成 WHERE 中的两个标量子查询：热点改善，但稀疏词典约 5→31 ms；不能把这种写法等同于最终的单行派生表。
- 单独查询边界、再绑定参数：能选较合适的范围，但每个搜索多一次网络往返；最终改为 SQL 内的单行聚合，不增加客户端查询数。
- 自连接过滤在长文本下明显退化；额外 `(deleted,id)` 用户索引在候选样本中没有稳定解决派生表排序；均未作为正式方案落地。
- 单独先读取用户 ID 的候选仍会排序，直接读取深页完整字段又明显变慢，所以不把首页策略推广到所有页。

候选的单条 SQL 耗时与最终完整服务耗时口径不同，不能混算倍率。探索阶段曾因一次全表扩宽 UPDATE 触发测试连接超时；正式分布从初始分批插入构造，没有放宽应用超时。临时实验索引和数据随所属测试库销毁。

## 基准扩展

保留三档行数与原有 22 场景，增加 12 场景，当前每次 **1 项编排 / 34 个服务读负载**：小词典首/末页、包含/字面/未命中，热点高命中/中文/搜索末页，以及用户第二页、活跃用户搜索、字面搜索和包含已删除用户的首页。

新增 `--list-perf-distribution`，默认 `standard`；所有分布均为确定性合成数据，不代表生产概率：

| 分布 | 热点及文本/删除特征 |
|---|---|
| standard | 保持原始样本：一半单词连续属于词典 10；原标签和删除/NULL 分布不变 |
| spread | 热点仍占 50%，但 ID 打散；其余单词分散到其他词典 |
| sparse | 热点占 1%，ID 打散 |
| dominant | 热点占 90%，ID 打散 |
| deleted | 热点占 50%，ID 打散；每 20 条才有活跃候选，每 7 条删除标记 NULL，约 4.3% 活跃 |
| wide | 热点 50%、ID 打散；词条文本填到 255 字符，包含 NULL 英/中文；needle 约每两条出现一次；用户简介 255 字符，合成无效密码占位串 162 字符 |

打散使用整数排列，没有随机种子或运行时随机数据。wide 密码占位串不是凭据，未用于登录。大小词典、热点占比、ID 局部性、删除/NULL 比例、文本长度和命中率都有明确取值；仍不是全分布穷举。

报告新增分布名称/完整参数及 `dataset_sha256`。比较除了环境、行数和完整结果，还拒绝生成器或分布变化；旧报告仅在两侧都缺省这些字段时保持历史比较能力。应用源码摘要允许变化，数据生成器摘要不允许变化。**旧 22 场景报告不能直接与本批 34 场景混比。**

## 实测与剩余成本

本机 MySQL 8.0.42、Python 3.11.17、6 逻辑 CPU、64 MiB InnoDB 缓冲池、REPEATABLE READ、utf8mb4_0900_ai_ci。六组 medium 和一组 large 各预热一次、测量三次；**七组各 34 个前后完整结果摘要一致**，可选写探针后也全部一致。另有 large 独立复跑，sparse/deleted 各以五次采样复核，smoke/1 私有实例入口通过。

large 标准分布，中位服务 ms：

| 场景 | 原 0008 SQL | 最终 SQL | 最终 SQL 独立复跑 |
|---|---:|---:|---:|
| 热点包含搜索 | 322.90 | 131.09 | 120.27 |
| 热点字面搜索 | 278.00 | 134.16 | 121.32 |
| 热点未命中 | 258.17 | 129.20 | 123.90 |
| 热点搜索末页 | 618.19 | 247.40 | 256.18 |
| 无搜索用户首页 | 30.81 | 16.33 | 15.58 |
| 用户深页（SQL 未变） | 41.53 | 42.31 | 43.66 |

large 的估算计划中，热点 COUNT 从 `ix_word_dict_deleted_id` 的 ref 改为 `PRIMARY` range，单语句中位约 315.51→126.48 ms；边界表为单行 system。用户首页的字段读取从覆盖评分索引的全候选排序改为短的 PRIMARY 顺序读取，约 17.18→0.60 ms，COUNT SQL 未变。这是计划和客户端执行计时，不是数据库 CPU 或实际扫描行数。

medium 的 standard/spread/dominant/wide 包含搜索分别约 **52→29、66→45、92→52、205→170 ms**。wide 搜索末页仍约 **343 ms**，不是已解决长文本规模成本。

**明确未通过全场景性能收尾：**

- 三次采样中 sparse 包含搜索约 7.91→8.07 ms、deleted 字面搜索约 8.01→8.80 ms，deleted 用户首页约 2.72→3.93 ms。
- 五次复核中 sparse 字面搜索约 4.79→6.43 ms、搜索末页约 3.84→6.61 ms；deleted 用户首页约 2.11→3.19 ms。这些退化保留为 N1 待办，不用“大场景提速”抵销。sparse 单词计划仍走词典索引，新增聚合并未减少其候选；deleted 用户页仍走评分索引，原先覆盖读约 860 个 ID 再取本页，改为直接取字段后需更多回表。
- 小词典存在聚合/规划开销；部分前后差异同时伴随未修改查询的整体抖动，不能把全部波动归因于 SQL，也不能因此忽略不利样本。未修改的用户搜索、大厅等耗时变化不作为本批收益。
- SQL 计时不是服务器 CPU 时间；串行预热、非独占宿主、估算 EXPLAIN 和少量样本均不足以证明冷缓存、吞吐或生产分位延迟。方法边界沿用 [第一批记录](LIST_PERFORMANCE.md)。

两项已有写探针仍分别为 5000 行真实 CSV 导入、100 行合成 Rating UPDATE。本批没有修改写路径、索引或评分；例如 large 中位约 **440→420 ms / 12.72→11.42 ms**，只记录波动，不宣称写入加速。探针数据恢复后核对全部读取摘要；**它仍不是完整对局结算或写竞争压测**，后者属于 N4。空间报告保留实际估算值，不把统计差异当作本批新增索引。

本机原始报告：`/tmp/wm-n1-before-<分布>.json`、`/tmp/wm-n1-final-<分布>.json`；large 对应后缀 `large`，复跑为 `wm-n1-final-repeat-large.json`。五次复核使用 `wm-n1-repeat-before-{sparse,deleted}.json` 与 `wm-n1-final-repeat-{sparse,deleted}.json`。`wm-n1-after-*` 是中途“额外查询边界”的候选，不是最终实现；不得混用。报告是本机证据，不是仓库运行依赖。最终成对报告、复跑、检查日志及前后两份业务源码/基准快照，已逐字节归档至本机已忽略的 `performance-results/n1-04785cf52735487ea8c4a538c99c7786/`，含 SHA-256 `manifest.json`；没有改写报告，也未上传。
